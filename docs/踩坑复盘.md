# 踩坑复盘

按发现顺序写的，每条都是「现象 → 根因 → 修法」。

有一半的坑不是模型不行，是**指标在骗我**或者**配置没对齐**。这个比例本身就值得记下来：
做 RAG 最贵的成本不是调参，是分不清「系统坏了」和「尺子坏了」。

---

## 1. 制度文件的标题没被识别出来，切分直接崩

**现象**：一份考勤制度解析完只有 21 个块、10 个标题。那份文件实际有 8 章 28 条。

**根因**：我的标题正则只认 `#`、`一、`、`（一）` 这几种，不认 `第X条`。
而中文制度文件里**「条」才是主力的层级**。不识别它的后果是整章被压成一个大块，
「第九条怎么规定的」这种精确问法直接召回不到——不是排序问题，是这个块根本不存在。

**修法**：补 `第X条 → level 2`。修完同一份文件 21 块 → 60 块，10 个标题 → 38 个标题。

但补正则时立刻踩到第二个问题：`第一条　为规范公司考勤管理，制定本制度。`
这句以「第一条」开头、长度不足 40 字，被误判成标题，层级全乱。
所以加了守卫：**标题不会以句读符号收尾**（句号、逗号、分号都不行）。两条都写了测试。

> 通用一点：切分是 RAG 效果的上限，而切分质量 90% 取决于标题识别。
> 每种文档类型的标题语法都不一样，一上来就应该拿真实文件看解析结果，别拿 Markdown 试。

## 2. 父块也参加了相似度竞争，把召回挤没了

**现象**：改成父子块之后，召回反而变差，top5 里翻来覆去是同一批大块。

**根因**：父块文本长、覆盖信息全，和任何问题的相似度都不会太低。
它本来只是"命中子块之后回填给模型看的上下文"，我却让它直接参与了检索排名。

**修法**：父块照样写进 Qdrant（回填时不用二次查询），但检索时用 payload 过滤
`must_not {kind: parent}` 排除掉。**小块负责准，大块负责完整，这两件事不能用一个尺寸同时满足。**

---

## 3. 混合检索用了加权求和，权重怎么调都是玄学

**现象**：稠密 + 稀疏两路召回，融合用 `w1*dense + w2*sparse`，调了一下午权重，换个问题分布就失效。

**根因**：两路分数根本不是同一种货币。稠密是余弦相似度（0~1），稀疏是词权重内积（无上界）。
直接相加，等于让量级大的那一路单方面决定结果。

**修法**：换 RRF，只用名次不用分数：`score = Σ 1/(k + rank)`，k=60。
免调参，对分数尺度免疫。

顺带测出一个反直觉的结论——**稀疏检索不是免费的午餐**：

| 配置 | easy(39) hit / MRR | hard(19) hit / MRR / keyword |
|---|---|---|
| 仅稠密 | 1.000 / 0.941 | 1.000 / 0.870 / 1.000 |
| 稠密 + 稀疏 | 1.000 / 0.954 | **0.947** / 0.947 / **0.895** |
| 稠密 + 稀疏 + 重排 | 1.000 / **0.974** | 1.000 / 0.947 / 1.000 |

hard 集（语义改述）上，稀疏把 MRR 拉高 0.077，同时把 hit@5 从 1.000 压到 0.947。
字面词权重把不相关块顶上来，挤掉了正确的。加回重排才恢复。
所以「混合检索一定更好」是错的，取决于你的业务更怕「排不靠前」还是更怕「该召回的被挤掉」。

## 4. 拒答阈值是拍出来的，静默误杀了一批好答案

**现象**：一开始觉得「分低就拒答」，随手设了 0.3。

**根因**：阈值不是通用常数，它是**分数分布的分位点**，和 embedding、reranker、语料三样都绑死。
0.3 在这套语料上漏放 80% 的负样本；换个 reranker，同一个数字直接从「太松」变「太严」。

**修法**：先标定再启用。39 条正样本最低 0.926，15 条负样本最高 0.571，
间隔 0.355 → 取中点 **0.748**，再留 5% 安全边际往「少误杀」方向压。

另外记一条：**没标定就干脆不设阈值**。宁可让生成层的 prompt 兜底，
也不要用一个假阈值误杀——误杀是直接丢答案，漏放只是多调一次模型。

还有一个当时没想明白、后来才想清楚的结论：

> 关掉阈值，拒答准确率**没变**（都 1.000），因为 prompt 已经兜住了。
> 阈值真正省的是模型调用：**36 次 vs 51 次**。
> 它不是准确率工具，是成本与延迟工具。别把「指标没变」当成「改动没价值」。

## 5. 指标在骗我：文档级 hit 饱和了

**现象**：三套多轮策略跑出来，检索指标全是 1.000，任何优化都测不出差别。
一度以为自己写了套无效代码。

**根因**：我用「文档级命中」当指标——一篇文章被切成几十块，只要任意一块进 top5 就算命中。
小语料上这个指标必然饱和。**它测的是「有没有找到这篇文档」，不是「有没有找到那句话」。**

**修法**：补 span 级指标（含答案关键词的那一块排第几）和 MRR。补上之后差别立刻出来：

| 策略 | hit@5 | MRR | keyword | spanMRR |
|---|---|---|---|---|
| 裸问 | 1.000 | 0.875 | 0.917 | 0.736 |
| 拼接上一轮 | 1.000 | **0.958** | 1.000 | 0.889 |
| 改写 + 双路 | 1.000 | 0.917 | 1.000 | **0.958** |

**MRR 和 spanMRR 给出了相反的排序。** 改写让答案块更靠前，但有一条用例（「那机密级呢」）
文档级排名从 1 掉到 2，于是 MRR 反而低。两个指标都要报，只看一个会得出相反结论。

## 6. 评测集本身有 bug，三个假信号

**现象**：coverage 突然从 0.962 掉到 0.816，看起来像系统退化。查了半天，是我的标注写错了。

1. **参考答案写成了条款摘要。** 问「A 级供应商账期多久」，我在 reference 里把 B 级 C 级也写上了。
   判分器认为答案漏答 → coverage 假跌。改成「只写回答该问题所必需的事实」后回到 0.962。
2. **关键词带语序。** 金标写 `十天育儿假`，答案写「育儿假……每年 10 天」，匹配不上。
   关键词必须是**最短可判定片段**（`10天`）。
3. **数字写法不一致。** 金标 `30 分钟`，模型答「三十分钟」。加了一层文本归一
   （中文数字转阿拉伯 + 去空白），但**刻意不展开「万/亿」**——`五十万` 展开成 500000
   反而和原文「50 万」对不上。

**现在的习惯**：指标掉了，第一反应不是改模型，是先看评测集。
判断方法很土但有效——把同一份答案跑两遍，如果判分波动超过 1 条，说明判分器本身有噪声。

## 7. 多轮改写的守卫判错，把正确的改写丢了

**现象**：追问「那海外呢」，改写模型正确补全成「海外差旅住宿费上限是多少」，
但守卫判定它离题，丢弃改写，等于白改。

**根因**：守卫用「改写结果与上一轮问题的相似度」判断是否跑偏，阈值 0.50。
可上一轮本身就是零内容追问，两句话天然不像。

**修法**：改成**和最近两轮比，取最大值**：0.25 → 0.80，误判消失。

同时踩到第二个坑：不能用「有没有被改写（changed=True）」判定话题跳转。
LLM 会顺手把自足问题润色一下，changed 就为真，跳转判定会误触发。
**跳转只能看相似度，不能看有没有改写。**

兜底是双路召回：改写问题权重 1.0、原问题 0.7。改写跑偏了，原问题那路还能捞回来。

## 8. 推理模型把 token 全花在「想」上，返回空字符串

**现象**：个别问题答案区一片空白。不是报错，就是空的——这种最难查。

**根因**：接的是带 reasoning 的模型，1024 token 预算被思维链吃满，`content` 返回空串。
HTTP 200、无异常、日志干净。

**修法**：检测空回答 → 预算提到 2048 重试一次 → 仍为空就返回统一拒答文案，
不让空白流到前端。流式路径同样兜底（流到一半为空也要补）。

> 发现它靠的不是日志，是前端「有引用卡片但正文空白」这个反常组合。
> 所以我把拒答原因和检索分数都显示在页面上——异常有时比日志更早暴露。

## 9. 演示层在撒谎：语料、阈值、示例问题三处不自洽

**现象**：我自己跑评测全绿，别人第一次打开页面，满屏「最高分 0.42 < 阈值 0.77」，
直接判定「这系统是坏的」。

**根因**（三件事叠在一起）：

1. 服务索引的是旧语料（16 篇 / 110 块），问的是新语料（12 篇 / 494 块）里的内容；
2. 阈值是旧语料标定的 0.771，新语料应该是 0.7485；
3. 页面上我写死的一个示例问题，语料里根本没有。

**修法**：

- 语料目录和标定文件绑成一张表，用 `scripts/serve.py` 一个入口搞定，启动打一行横幅说明当前用哪套；
- 示例问题不再写死：服务启动时在当前索引上真跑一遍检索，答不出的不下发，一条不通就不显示；
- 页面顶部常驻「语料名 · 篇数 · 块数」，索引为空弹橙色横幅。

**教训**：指标好看 ≠ 用户能用。评测集上 0.974 的回答质量，挡不住一个写错的示例按钮。
所以拒答理由、检索分数、索引来源这三样，必须同时在界面上可见。

## 10. docx 不走「逐段遍历」，走 HTML 中间层

这条不算坑，算一个当时纠结过的决定，后来证明是对的。

**方案 A**：直接遍历 `docx.paragraphs`，靠 `paragraph.style.name` 猜标题层级。
**方案 B**：用 mammoth 把 docx 转成 HTML，再用和 Markdown 同一个 HTML 解析器统一成内部 IR。

选 B 的理由：方案 A 只能拿到「一段一段的文字 + 一个样式名」，标题层级、表格、
合并单元格全靠自己猜；转成 HTML 之后结构变成标准语义标签，和 Markdown 走同一条下游路径。
**四类文档最后只维护一套解析逻辑**，出问题也只需要在一个地方查。

代价是多一层转换、多一个依赖。

## 如果重做，我会改的三件事

1. **先写评测集，再写代码。** 现在金标是边做边攒的，导致前两轮指标全是假的（文档级 hit 饱和）。
2. **解析层第一天就用真实文件验收。** 我是拿自己造的 Markdown 试的，所以 `第X条` 这种
   中文制度文件最主力的写法完全没覆盖到。
3. **给「配置」写测试。** 语料 / 阈值 / 示例问题那次的坑，本质是三个独立变量没有约束关系。
   现在靠 `serve.py` 绑成一张表，但更好的做法是启动时断言「阈值文件的 meta.docs 与当前目录一致」。
