# 企业 RAG 知识库问答系统 · 自研型技术选型（方案 B）

> 状态：**v1.4 定稿 + 完整语料实测**（2026-11-04），实现见 §7
> 已确认约束：单机 ≥16G 显存 GPU（实际未使用，全链路走 API）；MVP 含多轮对话与指代消解；文档类型仅 txt / md / pdf / docx
> 锁定的取舍：Qdrant 不做迁移预研；回答模型走公网 API，不要求内网闭环  
> 适用范围：自建检索链路、需要控制解析质量与增量更新的企业内部知识库问答

## 0. 前提假设

| 假设   | 取值                                       | 若不成立的影响                          |
| ---- | ---------------------------------------- | -------------------------------- |
| 硬件   | 单卡 ≥16G 显存（如 4080/4090/A4000）            | 显存不足需把 rerank 或改写模型移到 API        |
| 文档规模 | 1 千～5 万份，切片后 10 万～300 万条                 | 超过 1000 万条需换 Milvus              |

| 数据类型 | 仅 4 类：`txt` / `md` / `pdf`（含扫描件）/ `docx` | 若要加 xlsx、网页、IM 会话，需补对应适配器（IR 不变） |
| 部署   | 单机 Docker Compose 起步，可迁 K8s              | 回答模型走公网 API，其余模型本地；若后续要求闭环，需换本地 32B（24G+）     |
| 回答形态 | 多轮对话 + 带引用的问答 + 文档溯源跳转                   | 若要生成报告/跨文档分析，需进阶层 Agentic        |

## 1. 选型原则

1. **优先优化"数据进得来、找得准"，而不是换更强的模型。** 实践中 80% 的坏答案来自解析失败或没召回，不是模型不会答。
2. **每一层都要能替换。** 用接口包住 Embedding / Rerank / LLM，避免绑定单一厂商。
3. **可测量。** 没有金标集的优化等于玄学，评测链路第一周就位。
4. **小模型做小任务，大模型做答案。** 16G 显存的最优分工：本地常驻 Embedding + Rerank + 改写小模型，回答交给 API 大模型。

## 2. 逐层决策表

### 2.1 应用与编排

| 项      | 选定                                          | 备选 / 切换条件                                    | 理由                                                                      |
| ------ | ------------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| 语言     | Python 3.12                                 | —                                            | RAG 生态全在 Python                                                         |
| Web 框架 | FastAPI + SSE（`sse-starlette`）              | —                                            | 原生 async，流式输出简单                                                         |
| 编排框架   | **LlamaIndex**                              | Haystack（要管道完全显式、逐步断点）；LangGraph（要做 Agentic） | Retriever / NodePostprocessor / QueryEngine 抽象最贴合 RAG，父子块、混合检索、重排都有现成组件 |
| 长任务队列  | Celery + Redis                              | Arq（更轻）；RQ                                   | 解析 + 向量化是分钟级任务，必须异步                                                     |
| 会话存储   | PostgreSQL 两张表 `conversations` / `messages` | Redis（仅做短期缓存）                                | 多轮上下文与改写历史都要可追溯、可回放                                                     |

**不选 LangChain 做主框架**：抽象层数多，出问题要翻三层源码；它的价值在生态连接器，而本项目数据源就那几种。

### 2.2 文档解析（决定效果上限）

**范围锁定**：仅支持 `txt` / `md` / `pdf` / `docx` 四类。这带来两个依赖层面的净收益：删除 Unstructured（重依赖）与 Excel 解析；同时 PDF 内部拆成两条通道。

**核心架构决策：统一中间表示（IR）**  
四个格式适配器各自解析，但都输出同一个 `Document` 结构，下游只走一条切分路径。这是让"加格式"和"改切分"互不影响的前提，也是后续换解析器的成本边界。

```python
@dataclass
class Block:
    type: Literal["title", "para", "table", "list", "code", "image"]
    text: str
    level: int | None        # title 的层级，用于父子块
    page: int | None         # pdf 才有

@dataclass
class Document:
    blocks: list[Block]
    meta: dict               # doc_id, title, source_type, sha256, dept, acl_tags
```

| 类型           | 选定方案                                   | 关键实现要点                                                                                  |
| ------------ | -------------------------------------- | --------------------------------------------------------------------------------------- |
| **txt**      | 内置读取 + **charset-normalizer** 编码探测     | 国内 txt 大量是 GBK/GB18030，直接 `utf-8` 读会整篇乱码。再按空行分段、按 `第X章` / `一、` / `1.1` 等编号模式提取**伪标题层级** |
| **md**       | **markdown-it-py** token 流             | 全项目解析质量最高的类型：标题层级原生存在，直接映射为 `section_path`。注意 GFM 表格、代码块（不要切碎）、内嵌 HTML                  |
| **pdf（文本层）** | **PyMuPDF（fitz）** + **pdfplumber** 抽表格 | 快速通道，每页毫秒级，字符为原始文本无识别误差                                                                 |
| **pdf（扫描件）** | **MinerU**                             | OCR 通道，GPU 上每页约 1–3 秒，必须独立队列并限流                                                         |
| **docx**     | **mammoth** → HTML → 共享 HTML 解析器       | 比 python-docx 省事得多，见下方说明                                                                |

**PDF 必须双通道，不要无脑全量走 MinerU**

|    | PyMuPDF 快通道 | MinerU OCR 通道    |
| -- | ----------- | ---------------- |
| 适用 | 有文字层（电子版导出） | 扫描件、图片型 PDF      |
| 速度 | 毫秒/页        | 1–3 秒/页（GPU）     |
| 保真 | 原始字符，零识别误差  | 有 OCR 误差，且会做版面重排 |
| 成本 | 忽略不计        | 占 GPU，需排队        |

判定逻辑：`sum(len(page.get_text()) for page in pdf) / page_count < 50` 判为扫描件，走 MinerU；否则走快通道。**一份 1000 页的电子版 PDF，全量走 MinerU 要半小时以上，双通道只要几十秒。** 只有在检测到多栏/公式密集且阅读顺序错乱时，才针对性回退到 MinerU。

**docx 为什么换 mammoth 而不是 python-docx**

python-docx 的 `document.paragraphs` 只含 body 顶层段落，表格内段落、文本框（`w:txbxContent`）、页眉页脚都拿不到；标题层级要靠 `p.style.name` 判断，而中文模板返回的是"标题 1"不是"Heading 1"，需要做语言映射；Word 的自动编号（1.1、1.2）根本不在 `text` 里，会导致标题层级断裂。

mammoth 直接输出语义 HTML（`<h1>`–`<h6>`、`<table>`、`<ul>`），标题层级和表格结构都是现成的，且与 md 共用同一个 `HTML → IR` 解析模块。代价是文本框、批注仍会丢——这类内容在企业文档里面占比很低，可接受。

**表格处理**：文本层 PDF 用 pdfplumber 的 table extraction，扫描件走 MinerU，docx 走 mammoth 的原生 `<table>`。三者统一转 Markdown 表格保留行列结构，**绝不 OCR 成流式文本**——丢行列对应关系是最常见的准确率崩塌点。

**必做清洗**：去页眉页脚/页码/水印/目录页、合并断行、剥离重复页脚、保留标题层级（作为父子关系来源）。

### 2.3 切分策略

| 项   | 取值                                                                   | 理由                             |
| --- | -------------------------------------------------------------------- | ------------------------------ |
| 主策略 | 递归切分（标题 → 段落 → 句）                                                    | 通用性最好，先跑基线                     |
| 子块  | 256～512 token，overlap 64（12–15%）                                     | 检索粒度；overlap 太小会切断语义           |
| 父块  | 1024～2048 token                                                      | 命中子块后整段喂 LLM，解决切片丢上下文          |
| 元数据 | `doc_id, title, section_path, page, dept, acl_tags, version, sha256` | 权限过滤与溯源全靠它；现在预留，二期加 ACL 不用重跑索引 |
| 表格块 | 单独成块，前置所属标题与表头说明                                                     | 表格脱离上下文无法理解                    |

**按类型的差异化参数**（切分器同一套，参数按 `source_type` 走配置）：

| 类型   | 父块边界      | 子块边界 | overlap | 要点                             |
| ---- | --------- | ---- | ------- | ------------------------------ |
| md   | H2 章节     | 段落   | 10%     | 层级天然，直接把 `section_path` 写进块元数据 |
| docx | Heading 2 | 段落   | 10%     | 同 md；表格必须带上所属标题                |
| pdf  | 目录/页边界    | 版面块  | 15%     | 双栏文档按栏拼接，避免左右栏交错               |
| txt  | 伪标题（编号/章） | 空行段  | 20%     | 无结构时 overlap 加大，否则语义断裂严重       |

**不要做**：按固定字符数硬切；整篇塞成一块；overlap 给到 50%（索引膨胀且重复召回）。

### 2.4 向量化与索引

| 项         | 选定                                     | 备选 / 切换条件                                        | 理由                                       |
| --------- | -------------------------------------- | ------------------------------------------------ | ---------------------------------------- |
| Embedding | **bge-m3** 本地 FP16（1024 维，稠密+稀疏一体）     | Qwen3-Embedding-0.6B（中文榜单更强，可同卡并存）               | 一次产出 dense + sparse，省掉独立 BM25 服务         |
| 向量库       | **Qdrant**                             | pgvector（已有 PG 且切片 <100 万、运维优先）；Milvus（>1000 万条） | 原生 dense+sparse 混合检索、payload 过滤可下推、单容器启动 |
| 稀疏检索      | Qdrant sparse vector（bge-m3 sparse 权重） | BM25（`rank_bm25` 内存版）                            | 同一索引内做混合，避免跨库合并分数                        |
| 融合        | **RRF**（k=60）                          | 加权求和（分数可校准时）                                     | 无需归一化两路分数，鲁棒                             |
| 元数据库      | PostgreSQL                             | SQLite（纯原型）                                      | 文档表、会话、任务状态                              |
| 原始文件      | MinIO（或本地卷）                            | —                                                | 溯源跳转要能回原文件                               |

> 选 pgvector 的隐性代价：它不支持 sparse vector，稀疏侧要另接 BM25 再跨库融合。"少一个组件"是用检索复杂度换的。

### 2.5 查询理解与多轮对话（MVP 核心增量）

多轮场景的召回衰减几乎全部来自**用户问题不完整**：

```
Q1: 差旅报销标准是多少？     → 正常召回
Q2: 那海外呢？               → 直接检索必然失败（缺主语、缺对象）
```

**四步设计：**

1. **触发判定**（省延迟，不每次都改写）  
   命中任一条件才改写：含代词（它/这个/那）、省略主语、连接词开头（"还有呢""那…呢"）、长度 < 8 字。
2. **查询独立化**（standalone question rewriting）  
   输入最近 3 轮对话 + 当前问题，输出完整独立问题。**改写模型与作答模型走同一个 API 网关的小模型**（本项目实测 `deepseek-v4.1-flash`，延迟 200~400ms）——开发机没有本地 GPU，且改写是高频低难度任务，用 API 小模型比在本地维护一份 8B 权重更省事。
   若后续要求全内网闭环，再换本地 Qwen3-8B-Instruct-AWQ（16G 卡放得下，约 5.5G）。**改写模型必须有"不许引入历史外实体"的强约束**，否则编造出的实体比不改写更糟。
3. **双路召回**  
   改写问题与原问题**分别召回**，RRF 一起融合。改写引入偏差时，原问题这一路能兜住——这是多轮场景最容易被忽略的保险丝。
4. **上下文裁剪**  
   生成时带最近 3 轮原文 + 滚动摘要（>10 轮触发），不带全量历史，避免上下文污染和 token 膨胀。

**多轮特有的四个坑：**

| 坑             | 应对                                              |
| ------------- | ----------------------------------------------- |
| 话题跳转后仍按旧上下文改写 | 计算改写结果与**最近两轮**提问的最大相似度，低于阈值判跳转、清空历史（只跟上轮比会误判，实测踩过） |
| 改写错误污染整轮检索    | 双路召回兜底 + 改写结果写入 `messages.rewritten_query` 便于归因 |
| 复用上一轮检索结果做缓存  | 不缓存跨轮检索结果，只缓存同一问题的 embedding                    |
| RAGAS 不支持多轮评测 | 自建多轮金标集：记录完整对话历史 + 期望命中文档 + 期望答案                |

**显存预算（16G 卡，若坚持本地化）：**

| 模型                    | 精度       | 显存    |
| --------------------- | -------- | ----- |
| bge-m3                | FP16     | ~1.5G |
| bge-reranker-v2-m3    | FP16     | ~1.5G |
| Qwen3-8B-Instruct（改写，可选） | AWQ INT4 | ~5.5G |
| KV cache + 并发余量       | —        | ~7.5G |

**走 API 的分工**：回答模型（DeepSeek-V3 / Qwen 系）用大模型 API，改写用小模型 API。本地只保留可选的 bge-m3 / bge-reranker 作为离线降级路径。
这是本项目最终的落地形态——开发机没有 GPU，而且 embedding 与 rerank 走 API 时**不需要在每台机器上维护模型权重**，部署成本低一个量级。代价是数据出内网，敏感场景需切回本地。

### 2.6 检索与重排

| 项  | 取值                                   | 说明                   |
| -- | ------------------------------------ | -------------------- |
| 召回 | 向量 top 30 + 稀疏 top 30（改写问题与原问题各一路）   | RRF 后取 20            |
| 重排 | **bge-reranker-v2-m3** 本地，20 → 5～8 条 | 单卡约 120–200ms / 20 条 |
| 拒答 | rerank 最高分低于**标定阈值**直接回"资料中未找到"，不进 LLM | 0.3 是拍出来的，实测放到 46.7% 的负样本；必须标定（见 §7） |
| 过滤 | ACL 检索时下推为 payload filter            | 绝不能在生成后过滤            |

### 2.7 生成

| 项         | 选定                                           | 备选                                 | 理由              |
| --------- | -------------------------------------------- | ---------------------------------- | --------------- |
| 主模型       | DeepSeek-V3（API）                             | Qwen3-32B + vLLM（须私有化时，需 24G+ 或双卡） | 中文长上下文与成本平衡好    |

### 2.8 评测与可观测

| 项          | 选定                                                                              | 说明                                   |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------------ |
| 评测框架       | **RAGAS**（faithfulness / answer_relevancy / context_precision / context_recall） | 四指标覆盖"检索错"与"编造"两类问题                  |
| 金标集        | 单轮 30～50 条 + 多轮 15～20 组（含对话历史）                                                  | 第一周就位，否则无法证明任何优化                     |

## 6. 明确的"暂时不做"

- **GraphRAG / LightRAG**：索引成本高、评测困难，等多跳问题成为主要 badcase 再上
- **ACL / 多租户**：MVP 不做，但元数据字段预留，二期不重跑索引
- **微调**：检索没解决好的问题，微调也解决不了
- **多模态图片理解**：先用 OCR 文本兜住，图片问答单独评估
- **自研前端组件库**：没有价值增量

## 7. 落地实录（2026-11-04）

代码就是这个仓库，M1～M5 已完成，142 个测试全绿，约 1.1 万行。

### 7.1 与本文档的三处偏差（都是环境逼出来的，不是随意改）

| 原方案 | 实际做法 | 原因 |
|---|---|---|
| 改写用本地 Qwen3-8B-AWQ | 改写走 API 小模型（`deepseek-v4.1-flash`） | 开发机无 GPU；改写是高频低难度任务，API 小模型延迟 200~400ms 可接受 |
| embedding / rerank 本地 bge | 走网关的 `qwen3.7-text-embedding-flash` + `qwen3.7-text-rerank` | 同一网关已提供，省去 5G 权重与 GPU 依赖；本地 bge 实现保留为降级路径 |
| 拒答阈值经验值 0.3 | **不设默认值**，必须用正负样本标定 | 实测 0.3 会放过 46.7% 的负样本（"员工宿舍怎么申请"能拿 0.66 分） |

### 7.2 实测数字

**检索基线（16 篇语料 / 110 块 / 18 条金标）**

| 配置 | hit@5 | MRR@5 | spanMRR |
|---|---|---|---|
| 仅稠密向量 | 1.000 | 0.972 | 0.972 |
| 稠密 + 稀疏 | 1.000 | 0.972 | 0.972 |
| 稠密 + 稀疏 + 重排 | 1.000 | **1.000** | **1.000** |

**多轮对比（12 条，全部是"零内容追问"）**

| 策略 | hit@5 | spanMRR |
|---|---|---|
| 裸问 | 0.833 | 0.625 |
| 拼接上一轮问题 | 1.000 | 0.917 |
| 改写 + 双路（LLM） | 1.000 | **1.000** |

关键结论：**朴素拼接能拿回大部分收益（0.833 → 1.000），改写真正的价值在 spanMRR（0.917 → 1.000）——
它不是"多加点词"，而是"不乱加词"。** 拼接会把上一轮的限定词（"工作日加班"）一起粘到新问题上，
把错误的小节顶到第一。

**拒答阈值标定**

| 语料 | 正样本区间 | 负样本区间 | 间隔 | 阈值 |
|---|---|---|---|---|
| 16 篇 / 110 块 | 0.880 ~ 1.000 | 0.001 ~ 0.662 | +0.218 | 0.771 |
| 8 篇 / 42 块 | 0.712 ~ 1.000 | 0.002 ~ 0.692 | +0.019 | 0.662 |

**间隔宽度决定阈值可不可用。** 0.218 的间隔说明这批数据上阈值可靠；0.019 说明夹在窄缝里，
换一批文档就得重标。阈值还与 reranker 实现强绑定，换重排器必须重跑标定。

### 7.3 回答质量与前端（M5 的一部分）

检索指标只覆盖「找没找到」，所以补了一层回答判分（`scripts/evaluate_answers.py`，33 条用例）：

| 指标 | 数值 | 计算方式 |
|---|---|---|
| 拒答准确率 | 1.000 | 该拒的拒了、该答的答了 |
| faithful | 1.000 | LLM 判「每个结论在引用资料里有无依据」 |
| coverage | 0.944 | LLM 判 0 / 0.5 / 1 三档 |
| 答案含事实 | 1.000 | 确定性：关键词是否出现在答案正文 |
| 引用对位 | 1.000 | 确定性：被引用的块里是否真有该事实 |

两条判分设计原则，都是踩出来的：

1. **判分上下文必须和作答上下文一致**，包括来源行。第一版只喂正文，判分器把答案里的「国内差旅」
   当成编造，判了无依据。
2. **能确定性算的不要交给模型**（关键词、引用对位），模型只判「有无依据」和「要点覆盖」，
   且覆盖度只允许三档，避免伪精度。

**一个反直觉的测量结果**：关掉检索层阈值（0.771 → 关闭）后，拒答准确率仍是 1.000，
但模型调用从 36 次涨到 51 次。也就是说**在这一版数据上，阈值的收益是成本与延迟，不是准确率**——
生成层的 prompt 把 15 条负样本全拦住了。这不代表阈值可以去掉：prompt 兜底是概率性的，
阈值是确定性的第一道闸。但它说明指标没变不等于改动没价值，要看改动到底在优化什么。

前端 `web/index.html` 是单文件、零依赖的控制台，把三件平时看不见的事显式露出来：
改写后的问法、可展开的引用原文、拒答原因（`最高分 0.662 < 阈值 0.771`）。
一个坑：`citations` 事件给的是全部候选（6 条），第一版直接列成「来源」，
而答案只引用了 `[1]`——必须按答案里出现的编号过滤，否则读者会高估依据数量。

### 7.4 换成完整语料集之后的修正（重要）

§7.2 的数字来自 16 篇合成小语料，全部满分，测不出差异。补了一套 12 份完整制度
（`rag-kb/corpus_full/`，txt/docx/pdf/md 各 3 份，494 块）后，有些结论需要改写：

| 项目 | 小语料（16 篇 / 110 块） | 完整语料（12 篇 / 494 块） |
|---|---|---|
| 仅稠密 MRR | 0.972 | 0.941（easy）/ 0.870（hard） |
| 加稀疏 | 0.972（无变化） | 0.954（easy）/ 0.947（hard） |
| 加稀疏后 hit@5 | 1.000 | **0.947（hard）** |
| 加重排 MRR | 1.000 | 0.974（easy）/ 0.947（hard） |
| 正负样本间隔 | +0.218 | **+0.355** |
| 阈值 | 0.771 | **0.748** |

**结论一：稀疏召回是双刃剑，之前没看出来。** 在语义改述的问题上，它把 MRR 拉高 0.077，
却同时把 hit@5 从 1.000 压到 0.947——字面词权重把不相关块顶到前面，挤掉了原本能进前 5 的正确块。
小语料上所有配置都是 1.000，这个副作用完全不可见。

**结论二：阈值必须在自己的语料上标定，且要报告间隔宽度。** 完整语料的间隔是 0.355
（旧语料 0.218，demo 0.019）。默认的 0.3 会漏放 80% 的负样本，0.5 仍漏 13.3%。
**间隔宽度才是"这个阈值能不能用"的判据**，而不是阈值本身好不好看。

**结论三：MRR 与 spanMRR 可能给出相反排序。** 多轮场景下，改写 + 双路的 spanMRR 是 0.958
（高于朴素拼接的 0.889），但 MRR 是 0.917（低于拼接的 0.958）——因为改写把某一条的文档级
首条命中从第 1 推到第 2，却把答案块提到第 1。**只报一个指标会得出相反结论。**

### 7.5 评测方法本身也要被评测

这一轮最有价值的产出不是分数，是发现三个"看起来像系统退化、实际是标注问题"的假信号：

1. **参考答案写成了条款摘要。** 问 A 级账期，参考里连 B/C 级都写，判分器记成漏答，coverage 掉到 0.816。
   改成"只答所问"后是 0.962。
2. **关键词带语序。** `十天育儿假` 遇到「育儿假……每年 10 天」匹配不上。关键词必须是最短可判定片段。
3. **数字写法差异。** 金标 `30 分钟` vs 答案"三十分钟"，确定性匹配直接判 miss。
   为此新增 `evaluation/text_match.py`（中文数字转阿拉伯 + 去空白），并刻意**不展开「万/亿」**——
   `五十万` 展开成 500000 反而和「50 万」对不上。

还有一条是真 bug：跨文档题上推理型模型把 1024 token 预算全花在 reasoning 上，`content` 返回空串，
前端会显示空白。已加 1024 → 2048 重试，仍空则退回拒答文案。

**教训**：汇总数字只能看趋势，判断退化必须逐条看失败明细，否则会把标注错误当成模型不行。

### 7.6 两条本文档没写到、但很重要的经验

**1. 文档级 hit 在小语料上会失效。** 一篇文章被切成多块，任意一块进前 5 都算命中，
指标恒为 1，任何优化都测不出差别。必须补 **span 指标**（含答案关键词的那一块排第几）。
这是本项目一开始把 8 篇小语料当成评测集、结果三套策略全是 1.000 之后才发现的。

**2. 改写可信度要靠"和最近两轮比"。** 只和上一轮比相似度，在"上一轮本身就是省略式追问"时会误判：
实测「那海外呢」的正确改写被 guard 判成离题（相似度 0.25），改成最近两轮取最大值后是 0.80。
同类坑还有一个：LLM 把自足问题顺手润色一下，`changed=True` 就会绕过话题跳转判定——
所以跳转只能看相似度，不能看"有没有被改写"。

### 7.7 演示层会撒谎：语料、阈值、示例问题必须自洽

第一次真人打开页面，满屏「最高分 0.42 < 阈值 0.77」。测试 140 个全绿、评测集 hit 1.000、
拒答准确率 1.000——系统"按配置正确执行"，但看起来像坏了。三个原因叠加：

1. **示例问题是写死的，其中一条语料里根本没有。** 界面上摆着「员工宿舍怎么申请？」，
   `grep -rl 宿舍 corpus/ corpus_full/` 零命中。用户点它、又自己改写着重问四遍，
   连吃四记拒答，于是判定"都答不上"。**评测集上 0.974 的回答质量，挡不住一个写错的示例按钮。**
   → 示例改由服务端下发：启动时拿候选问题在当前索引上真跑一遍检索，被阈值拒掉的不透出去；
   一条都没通过时宁可不显示。
2. **语料目录和拒答阈值是两个独立环境变量，换一个忘了另一个。** 0.7708 是 `corpus/` 的标定值，
   `corpus_full/` 是 0.7485；拿 A 语料的分位点去卡 B 语料的分数，表现就是"全屏拒答 + 日志零报错"。
   → `scripts/serve.py` 把目录名与标定文件绑成一张表，启动打一行横幅说明当前用的是哪套。
3. **页面不显示索引来源。** 用户无从自查"我问的文档到底进没进索引"。
   → 顶部常驻「语料 corpus_full · 12 篇 · 494 块」，`/health` 也返回 `docs_dir`。

一句话：**RAG 的失败大多数不是模型不行，是配置和用户以为的那份知识库不是同一个。**
所以拒答理由、检索分数、索引来源这三样必须在界面上同时可见——它们比多 0.01 的召回率有用得多。
